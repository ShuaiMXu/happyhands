# 方法选择：一次真实 Harness 闭环验证

基线为 `d469a02`（#30 合并后），目标是 HappyHands 自己的项目设置，不是第三方产品的视觉改版。

## 实际缺陷与边界

已保存的 `typeset` 在设置弹窗中显示为空；桌面和手机下拉菜单均只有 `polish/layout/animate` 三项，而运行时支持十一项。诊断只录入这一项明确的能力不匹配，没有把长输入框正常裁切、弹窗滚动、菜单暂时遮挡背景或既有间距录成缺陷。

实现复用当前 Radix Select 和翻译入口，界面与后端校验共用浏览器安全的方法目录。编辑配置时保留已采用的 remediation，已有 `legacy-v2` 仅在编辑该配置时提供兼容选项，不恢复为默认路线。旧整改指南改为遵循绑定的专项 readFirst，再做 Polish，避免文字上仍只列 Layout/Animate。

## 方法是否实际参与

| 环节 | 观察到的实际行为 | 不代表什么 |
| --- | --- | --- |
| 有界处理器 | 实际调用八项；component-inventory、responsive-reviewer 完成，其余六项返回证据不足或能力边界 | 完成扫描不等于候选缺陷已成立 |
| Foundation 与组件状态 | 缺少 designFoundation，drift/state 处理器明确没有完成分析 | 不补造批准的 Foundation 来让流程全绿 |
| 模型诊断 | 新的只读会话读取绑定方法和四张 before 原图，仅录入缺失选项 | 没有证明 before 曾实际点击提交 |
| 隔离修复 | 真实 Codex 执行；完成事件中有 OJO、Impeccable Harden/Polish、web-taste 的读取命令；补齐状态、序列化及专项路线测试 | 读取记录不能证明理解，更不能证明所有 Skill 都运行过 |
| 操作验证 | 桌面与模拟手机上打开十一项菜单、Escape 返回焦点、键盘选 Extract，并由真实 configure 接口返回 200；读取落盘配置确认 intent=extract | configure 后的额外 onboard 请求被拦截，避免重复流水线；完整执行由外层真实 Run 承担 |
| 独立复核 | 另起只读会话检查原始前后图、差异和绑定的交互验证记录 | 最终人工采纳仍待用户判断 |

本次 portable CLI 的有界处理器由操作者按文档逐项调用，不宣称工作台默认自动调度已被这次验证。九个 contract-only 能力没有被当作已实现分析器，未调用的专项也没有被记为已使用。

被测项目保存的是 Typeset；本轮实际修复选用 Harden → Polish。Typeset → Polish 的路由由专项单元测试验证，不能把菜单可选直接记为排版专项已执行。

## 留痕与发布

初始采集计划漏开父级折叠区域，以及首次执行器启动被本机权限限制的失败均保留；成功执行使用带前驱引用的新 Run，没有覆盖失败记录。原图、运行记录、临时脚本和本地配置不随 PR 发布。

第一份独立复核输出没有被接纳为有效 QA：它检查了补充验证图片，并把这些图片也写进仅接受 before/after 采集原图的结构矩阵。原提示词要求“每张原图”，另一处又要求检查所有验证图片，范围没有说清。已改为列出精确的采集图片 × 五维度矩阵，并说明验证图片只能作为补充证据；新增测试仍要求拒绝多出的矩阵行，没有放宽校验器。原始输出保留，不能把协议修正记为该次复核通过。

用户随后明确指出方法字段排版不协调。浏览器计算样式确认，通用弹窗按钮选择器覆盖了 Radix SelectTrigger 的字段样式，使其值居中、边框为零；嵌套字段标签也没有继承直接子字段的网格间距。这一新增要求进入第三轮前驱关联修复，不把早先“保留现有布局”的判断覆盖成已完成排版验收。

第三轮修复从通用动作按钮规则中排除 SelectTrigger，复用现有字段边框、起始对齐和字重；项目设置内的嵌套标签继承既有 6px 网格间距。新增浏览器回归加载真实工作台样式入口，覆盖桌面／手机、浅色／深色、两个方法菜单、键盘和焦点、模拟配置载荷，以及页面审阅下拉框、普通按钮和复选框。测试明确使用夹具 API；另行绑定的验证才执行真实 configure 保存。

额外宽度验证的初版漏算了既有外边距。失败记录保留，后续按边框盒宽度加外边距计算实际占用宽度。没有为了让测试通过而修改产品间距；原图和源代码均未覆盖。

新增测试覆盖十一项翻译与校验、所有 taste/intent 配置组合的往返保留、显式 legacy 兼容，以及 Typeset → Polish／只读 Audit → Critique 路线。

UI 修复工作区的完整测试：758 项，751 通过、3 失败、4 跳过。三项失败均发生在 Windows 创建符号链接时，错误为 EPERM；没有删掉或放宽这些安全测试。设计检查、生产构建及 28 项反例回归通过。远端 CI 结果另列于 PR。

整理发布分支时还实际复现了导出缺陷：执行器把 `git diff` 当成展示文字调用 `trim()`，去掉末尾换行后，带新增文件／结尾空行的 `diff.patch` 被 Git 判为损坏。修复仅让该调用使用已有 `rawOutput` 通道。新增合成执行器回归先复现失败，再比较导出与原生 Git 输出的完整字节，并在干净基线上执行 `git apply --check`。它验证补丁运输协议，不冒充模型执行或 UI 验收。原损坏补丁保留，发布内容从实际隔离工作区重新导出；测试文件末尾多余空行在发布补丁应用时按 Git 标准清理，页面源码不因此改变。

这是一份观察记录，不是已接受的学习样例，也不自动生成新的全局审美规则或激活 expertise release。

## 最终独立复核

第三轮的独立只读复核已通过协议校验并保留：任务和层级两维通过；交互、设计系统、回归三维为 needs-evidence，整体同为 needs-evidence，没有新增明确缺陷。复核确认字段可识别性改善和真实 configure 保存，同时保留这些边界：

- 其他受影响消费者、深色及完整焦点／禁用／恢复状态的测试已有本地记录，但未全部作为本轮当前绑定原图交给该会话。
- 当前窄范围采集没有版本化 designSystem 前后快照、批准的 Foundation 和组件／token 差异对照；项目文档的采用依据不能替代这些证据。
- 手机底部主按钮贴近对话框边缘，尚缺完整滚动与触摸流程证据。复核没有据此推定新缺陷。
- 只读复核没有完整前驱执行日志，不能独立核实操作者描述的历史链和全部 Skill 使用；本记录据本地留痕说明，不冒充其独立结论。

因此 PR 保持草稿，不能宣称共享组件完整验收、全部 Skill 已应用或人类最终接受。补证应保留本次结论，继续使用不可变原图和真实状态；不补造 Foundation、覆盖失败或反复重审到得到 pass。
