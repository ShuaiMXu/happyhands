# HappyHands 同题评测与验收规则

对应 [Issue #14](https://github.com/ShuaiMXu/happyhands/issues/14)。**完整 Harness 同题验证待执行。**

两项预实验已记录。下列规则用于后续真实运行。Alpha.2 的已验收官网修复作为独立历史案例保留。

## 评测要回答的问题

先检验同一个可用的轻量模型走完整 HappyHands 后，是否比该模型直跑交付更好的产品体验。若要回答“能否达到或超过更强模型”，再加入一个本轮可实际调用的强模型直跑组。模型是每轮登记的实验参数。评测前验证实际调用权限，记录模型、工具版本、预算和失败原因。

| 组别 | 执行要求 | 可回答的问题 |
| --- | --- | --- |
| A 同模型直跑 | 通过普通执行器完成任务，提供原稿、源码和明确的用户目标及约束 | 直接交付的基线表现 |
| B 同模型加 HappyHands | 使用与 A 相同的实现模型，从真实 Harness 入口执行，提交可复核的运行记录 | 完整流程带来的质量与成本变化 |
| C 较强模型直跑 | 按本轮问题选用可调用的模型，使用与 A 相同的任务输入和验收标准 | 在该任务上能否达到或超过较强模型的交付 |

A、B 从同一源码和基线状态启动，登记素材、允许的修改范围、工具权限、资源上限和验收任务。模型宿主、配置和可用工具有差异时如实记录。诊断、参考、实现、复拍、复核和人工返工都计入流程成本。只额外提供规划上下文的实验记为预实验。需要定位增益时，在完整对照之后逐项移除项目记忆、参考决策或复核，记录受影响的结果。

## 完整 Harness 运行的证据

以下按现有 [编排](experience-orchestration.md) 和 [轻量运行指南](../skills/happyhands/references/workflow.md) 执行。一个评测案例应能通过同一运行目录追溯输入、代码和输出。

| 顺序 | 执行入口与方法 | 评测要核对的证据 |
| --- | --- | --- |
| 1. 定义任务与采集原稿 | `start`、`capture --phase before`。明确访客任务、当前页面及应保留的设计，读取项目 DESIGN.md、设计系统和既有组件 | 有效的源码绑定、原始截图和相关交互状态 |
| 2. 诊断当前页面 | `model-diagnose`。用本项目整改规则、OJO 与适用的 Taste 方法，先逐条核对 AI slop 和控件细节，再查共享组件、用户路径、内容层次与栅格 | 每条实际问题有截图或交互证据，说明任务影响。保留排除理由及缺证项 |
| 3. 规划与隔离修复 | `confirm` 或 `repair-scope`，再用 `plan`、`execute`。按项目规范决定内容去留、主操作、尺寸间距和组件状态，依据 OJO 与选定方法修复根因 | 已确认或授权的范围、绑定的方法与参考、隔离工作区、逐条处理结果及代码差异 |
| 4. 复拍与检查 | `capture --phase after`、`verify`、`evaluate`。先验原问题和当前页面状态，再查共享组件消费者和其他端 | 匹配的前后原图、键盘等实际交互记录、适用检查的结果和失败记录 |
| 5. 独立复核与人工判断 | 独立的 `model-review` 或受支持的独立证明，再用 `compare` 提供成品与证据；用户给出判断后通过 `judge` 记录 | 独立审查结论、剩余问题和用户接受或拒绝的记录。采集案例后按现有流程决定是否纳入长期规则 |

### 如何报告状态和结论

- **待执行或进行中**。明确当前阶段。诊断、代码改动、截图或模型结束事件只计入各自步骤。
- **阻塞或失败**。记录出错步骤、可核对的原因、尚缺证据以及已产出的材料。缺失的对照组保留为缺失，继续有条件执行的组。
- **待人工验收**。实现、匹配复拍和独立复核已通过，等待人判断产品结果。拒绝时记录原因，修订后的新运行保留与旧运行的关联。
- **已验收**。本轮作用域内的真实运行证据齐全，适用检查和独立复核通过，用户明确接受。用运行 ID 和验收记录支持这个状态。

评测结论另行记录。功能和保留约束通过后，再将原稿与产出匿名编号，按任务可达性、信息结构、操作状态、布局与内容取舍、个人或品牌表达做盲评。允许选择原稿、平局或证据不足，保留具体理由。先报告 A 与 B 的同模型结果。只有 C 实际产出并完成同条件评审，才报告跨模型结论。稳定收益需要多个真实任务和复跑支持。

## 产品取舍

| 交给模型 | 由项目和 HappyHands 保留 | 如何验证 |
| --- | --- | --- |
| 找出候选问题、提出设计方向、生成和修改代码 | 用户任务、品牌及个人表达、已有组件、允许修改的范围 | 换模型后重放同一任务，记录用户是否需要重复解释约束、是否出现已知回归 |
| 阅读参考、生成方案和解释取舍 | 任务匹配的参考版本、适用区块、采用与舍弃的理由 | 保持同一基础输入，移除参考决策，对比结果是否仍满足相同任务和表达 |
| 分析截图、给出复核意见 | 同状态原图、源码版本、差异、功能检查、人的接受或拒绝 | 让另一位操作者只靠记录复核结论，检查缺失或变化的证据能否被发现 |
| 从历史案例提取候选经验 | 人工确认的适用范围、例外、撤回和历史证据 | 跨任务重用时记录误用与返工，撤回或失效的案例应退出后续计划 |

可先复用 [设计来源集成](design-md-integration.md)、[项目记忆](project-memory-lifecycle-2026-10-18.md)、[历史案例](experience-cases.md) 和 [轻量 CLI](lightweight.md)。项目决定随仓库或本地运行保存。观察结果、候选规则和人工确认各有独立状态。模型升级后先用原记录复跑，依据结果调整流程和投入。

Alpha.2 已证明一次真实官网修复可以保留匹配原图、代码改动、独立复核和明确的用户接受记录。它覆盖语言同步、错误恢复和键盘入口。该案例没有同期模型直跑对照，也没有让用户评价新的视觉方向。[Alpha.2 发布记录](https://github.com/ShuaiMXu/happyhands/releases/tag/v0.1.0-alpha.2) · [官网修复 PR](https://github.com/ShuaiMXu/happyhands-site/pull/73)

## 官网预实验

2026-11-11，HappyHands 官网接入页，源码提交 `e47570fc6a14bc807986634aaf2ee3f57a62a967`。两个隔离副本的 Git tree 都是 `aabf3e11db71ccd184017b0398ca85f3e9fac705`。各用 Codex CLI 0.167.0、GPT-6 Astra、medium、8 分钟上限和相同六张基线原图。两组都能读源码和项目规则。上下文组额外获得已确认的保留约束、证据映射和版本固定的 Lime Field 参考及其采用与舍弃理由。旧补丁和旧评审结果未作为输入。这组实验只比较附加规划上下文，完整 Harness 的验收能力来自独立的 Alpha.2 已验收案例。

| 实现方式 | 桌面与手机交互 | 实现耗时 | CLI 报告 token |
| --- | --- | ---: | --- |
| Astra 直跑 | 两端各 16 项通过，无横向溢出 | 128.55 秒 | 输入 401,534，其中缓存 350,208，输出 2,752 |
| 同模型加规划上下文 | 两端各 16 项通过，无横向溢出 | 178.72 秒 | 输入 454,334，其中缓存 413,312，输出 4,447 |

两组都通过类型检查和差异格式检查。交互包括中英切换、草稿与 DSH 选择保留、当前错误反馈、顺序 Tab、Enter、空格、原生链接和焦点。有效链接未打开。没有针对视觉风格进行人工评分。用时是这两次实现的实际墙钟时间，token 包括缓存，账单金额没有从该数据推算。

在这个目标明确且保留现有视觉的任务里，附加上下文没有提高检查通过数，且本次实现多用约 50 秒。通用修复指导可以从短版开始。品牌取舍有争议、任务跨轮次或需要设计探索时，再验证上下文与参考决策是否减少具体返工。现有项目记忆、经验案例、参考快照的 24 项工程回归通过，能支持证据和规则的存取与失效检查。

## 作品集预实验

用含示例人物和项目的开源作品集模板，先检验实验方法。目标是让访客从首屏进入作品，保留姓名、职业、第一人称介绍、既有作品和主题切换。两组都使用 GPT-6 Luna，读取相同源码和桌面、手机原图。上下文组还收到两种候选方向、任务相关参考和取舍说明。两组均成功构建。在 1440 × 900 和 390 × 844 下，两个改稿都保留了原介绍和项目标题，首屏内的作品入口可用 Enter 到达作品区，浅色与深色可以来回切换，未见横向溢出。

两版的布局和信息取舍仍需人工盲评。评审特别检查首屏能否在短时间内说清“是谁、做什么、作品在哪”，以及重复的身份信息、眉标、装饰编号和标签是否稀释主次。模板用于试验任务与验收规则，仍需内容完整的实际作品集检验个人表达。当前没有较强模型的同题产出，也没有完整 Harness 同题结果。

## 后续案例

- **功能型产品**。沿用官网接入页的已固定基线与交互任务，新增同模型完整 Harness 组。记录语言、当前错误提示和键盘操作的证据，检查修改后是否保留原设计和共享组件契约。
- **个人作品集**。用经授权、内容完整的作品集检验个人表达。登记作者语气、原图和真实作品。探索任务在精修前比较两个方向，写清参考如何服务访客任务，以及哪些现有表达要保留。盲评时让原稿一同参加，核对作品入口、首屏层级和冗余信息。
- **迭代与复跑**。更换模型时继续使用已锁定的任务和验收规则。用重复运行判断哪些项目资料或整改步骤能稳定减少约束丢失、返工或证据缺口。长期规则沿用现有案例收录流程，保留适用条件、例外和历史记录。
