# Product brief

**Who:** Independent developers and small teams who shipped an app with vibe coding and know it could be better, but lack a product designer to diagnose and guide the next change.

**Job:** “Show me the most important experience problem in my working product, fix it with my coding agent, and prove the result is better. When I add a new page, establish the design system first and keep the result consistent as the product evolves.”

**Positioning:** A continuous AI Product Designer for the post-build stage. It complements Codex's implementation ability with product judgment, evidence, prioritization, visual/interaction evaluation and project memory.

**Initial promise:** Connect a runnable app, choose a key user task, and receive one clear, evidence-backed improvement opportunity within five minutes. For a missing surface, review and approve its Design Foundation before generating the first page. A full review can examine more pages and flows; a continuous plan watches future changes.

**Differentiation:** A reusable Experience Spec; an extracted and governed brand/design foundation; explicit expert loop; before/after proof; human judgment capture; versioned expertise and evaluator; incremental project history. A static skill or one-off report can imitate parts of this, so the product must earn its value through reliable outcomes and accumulated context.

**Out of scope for the first slice:** Autonomous redesign of an entire app, unsupported “perfect” scores, automatic claims about conversion without behavioral data, and site generation before the evaluation loop works.

## Agent-native product shape and distribution

Hypit's presentation is a useful reference for **how the product is packaged and discovered**, not for what it produces. Our equivalent entry is: connect a vibe-coded app or paste a preview URL, name the user task, and get a reviewable improvement. The deliverable is an editable Experience Spec, a scoped code change, and before/after proof; future reviews can reuse the same project context.

After the MVP loop works on real apps, expose it through:

1. A public, runnable demo with an actual before/after app case and the evidence behind the recommendation.
2. An agent-native Skill/CLI that works inside Codex or another coding agent, with the spec and evaluator kept in the project.
3. A hosted service for the work users do not want to operate themselves: broad diagnosis, browser runs, change monitoring, review history, and managed expert updates.
4. A starter path from an app URL/repository, a design reference, or a concrete problem statement. All paths produce the same Experience Spec and validation artifact.

The message should be outcome-first: “Your app works. Make it feel designed.” Show one concrete problem, the code change, and the measured or observed improvement. Avoid unverified score jumps or claims of perfect design. Open distribution can make the workflow easy to try; the paid value has to come from reliable judgment, the complete loop, and continuing project memory.

This packaging follows Hypit's visible agent/Skill entry, editable workflow, template/reference starts, demo and hosted API pattern. It is a **product hypothesis** to test, not evidence that the same commercial model will work for UX improvement.

## Appllama case: free expertise as the distribution layer

Appllama sharpens the distribution hypothesis. Its public repository separates a research Skill from an implementation Skill, installs across agent hosts with one command, and connects those methods to a paid MCP backed by proprietary mobile-app evidence. The reusable method is open; the scarce data and operated service remain paid.

The Product Designer equivalent should have three explicit layers:

1. **Public Product Designer Skills** teach an agent how to inspect a post-build product, collect evidence, diagnose one bounded problem and invoke the local Harness. They are the trial surface and professional proof, not the whole product.
2. **The Harness** owns the trustworthy loop: replay task states, route versioned Skills, preserve the Design Foundation, scope the code change, render the same states, run evaluators and capture human judgment.
3. **Managed project intelligence** is the paid layer: Deep Review delivery, broader browser execution, project memory, incremental monitoring, expert/evaluator upgrades and cross-project regression knowledge.

The product must remain useful when the paid layer is absent: a developer can install a Skill, run a local bounded review and inspect every artifact. Payment buys operation, continuity and improving judgment rather than access to a hidden prompt.

This case also raises the quality bar for our Skills. A strong public Skill needs concrete laws, explicit inputs, named failure states, a replayable verification loop and a definition of done. It cannot end with subjective advice such as “make the page cleaner.” Unlike Appllama's pre-build mobile focus, our public proof should start from a working vibe-coded product and show the same task before and after a governed change.

The website should make this architecture legible without exposing implementation jargon in the main journey:

- **Try locally:** install the public Skill and review one task.
- **See proof:** inspect the HappyClaw evidence, change and evaluation.
- **Get it done:** purchase a managed Deep Review.
- **Keep it good:** subscribe to project memory and incremental review.

Treat Appllama as evidence that the packaging is understandable and distributable, not as proof of willingness to pay for our post-build workflow. That still requires observed completion and payment behavior from independent developers.
