# 组件与设计系统审阅缺口

## 已确认的原因

1. 自动提取组件只认 `components/`、`ui/` 目录，漏掉原生 HTML/JS 项目中由页面加载的 UI 模块。
2. 默认诊断运行可访问性、响应式、信息架构与视觉层级，未默认运行设计系统差异、组件状态与复用检查。
3. 修改指令要求复用已批准组件，却没有明确要求先检查现有规范、共享实现及其使用位置。缺少批准清单容易被误解成可以局部补样式。

## 已补的流程

- 原生组件候选同时要求 DOM 渲染代码与页面相对脚本/加载清单引用，记录来源和消费者，排除测试与输出目录。远程链接、未引用模块和纯请求工具不会仅凭文件名成为组件。
- 默认与增量诊断检查设计系统差异和组件状态。确认方向后，在统一的计划生成入口执行组件复用规划，将 `component-reuse-plan.json` 写入计划及执行说明，并随审阅记录导出。缺少清单时保留 needs-evidence，要求执行者先检查源码，不推断项目没有可复用组件。
- 修改前必须记录现有规范、复用的组件/变量、受影响使用位置及例外；修改后说明检查了哪些重复组件、设备和状态。候选可经源码检查后复用，但不自动批准成规则。

- `docs/UI_STYLE.md` 指定主工作台由 `web/apple-workbench.css` 收口；另有 `web/design-system.css` 的 `--color-*`、`--text-*`、`--radius-*` 系列。两套体系的品牌色、边线色、字号和圆角存在差异。需要按入口和实际加载关系确认规范归属，再建立别名或迁移，不应仅凭变量名字批量替换。
- `web/ui-dialog.js` 内嵌对话框样式，任务侧栏、看板和主工作台也分别定义圆角、间距、控件样式。应先对齐确认框、按钮、输入框、状态提示这些反复出现的模式，保留业务看板的特殊布局。
- 组件状态清单尚不完整。默认、悬停、焦点、禁用、加载、错误与空状态需要按真实组件分别验证，不能靠默认页面截图宣布完成。

后续代码审阅发现复用规划曾在确认问题之前运行，因缺少 finding 而没有结果。已移至确认后的计划阶段，覆盖普通审阅、设计方向和画布请求共用的入口。旧的诊断产物保留，新计划单独记录当前 finding、修改意图、已批准组件、待核对候选和局限。组件适配性仍须检查源码 API、使用位置和实际状态，生成候选清单不等于已完成设计系统迁移。
