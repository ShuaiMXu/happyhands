# 持续 AI Product Designer：产品与系统架构

## 产品要解决什么

目标用户是已经用 vibe coding 做出产品的独立开发者和小团队。他们通常能把功能做出来，也能让编码 agent 修改代码，但缺少设计师的判断：哪里最影响用户、为什么先改这里、怎样才算改好，以及下一次迭代有没有把体验重新做坏。

产品交付的不是一份 UX 报告。它要找到当前最值得解决的体验问题，完成一次可审阅的修改，用前后证据验证，并随着项目变化持续复查。

编码 agent 是执行引擎。我们的产品负责设计判断、证据、优先级、验收和项目记忆。两者组合后形成持续在线的 AI Product Designer。

## 用户看到的产品形态

工作台使用一个共享空间：左侧按项目文件夹组织审阅记录，页面审阅、审阅报告、代码改动和设计方向只切换中间视图。AI 诊断后进入当前记录的设计方向，确认范围并生成计划后返回画布查看细节和批注；切换视图保留当前记录与已选择方向。旧的运行记录设计方向地址自动转入共享空间，历史演示页不作为当前记录的诊断来源。

```text
接入项目（仓库 + 可运行预览）
             ↓
选择核心用户与关键任务
             ↓
抽取现有品牌、Token、组件和交互模式
             ↓
5 分钟价值证明：证据 + 最重要问题 + 修改方向
             ↓
Deep Review：跨页面、跨状态的完整诊断
             ↓
选定一个问题并交给编码 agent 修改
             ↓
同状态、同尺寸重新渲染和验证
             ↓
用户 Accept / Reject 并说明原因
             ↓
把通过的 Token / 组件 / 模式回写为候选规范
             ↓
持续监控项目后续变更，发起增量 Review
```

第一入口可以是 `$20 Deep Review`，让用户低成本看到一次全面诊断和一个可执行的优先级列表。后续订阅卖的是项目级持续设计维护、变更监控、历史上下文和持续升级的专业判断。高质量网站生成放在下游：当诊断和验证能力可靠后，同一套 Experience Spec、组件约束和 Evaluator 可以驱动从零生成或大规模重构。

## 六层系统

### 1. Project Memory

保存产品目标、目标用户、关键任务、技术栈、品牌约束、历史页面状态、已接受和被拒绝的设计判断。它让下一次 Review 理解项目，而不是每次从一张截图重新开始。

### 2. Evidence Collector

通过浏览器和代码采集桌面/手机截图、DOM 摘要、页面状态、关键操作、源文件引用和构建结果。所有结论必须能追溯到证据；加载失败、错误遮罩或部署来源不一致必须显式暴露。

### 3. Design Foundation Registry

第一次 Review 同时盘点已有的品牌原则、语气、Logo 和图像资产、颜色/字体/间距/圆角/阴影/动效 Token、组件及其变体和状态，以及重复出现的交互模式。系统还要发现相同用途的不同颜色、重复组件、状态缺失和页面间不一致。

盘点结果分为 `observed`、`approved` 和 `deprecated`。`observed` 表示“代码里现在这样做”，不能自动等同于正确规范；设计师或产品负责人批准后，才成为后续 agent 修改必须遵循的约束。新修改产生的组件和模式也先作为候选更新，经过前后验证与人工接受后再进入正式系统。

### 4. Experience Intelligence

把证据整理为 Experience Spec，并完成诊断、影响判断、置信度、成本估计和优先级排序。未来的 Experience Score 应由多个可解释维度组成，并显示证据覆盖率和不确定性，不能只给一个看似精确的分数。

### 5. Expert Loop Harness

执行 `Diagnose → Confirm → Plan → Agent edit → Render → Evaluate → Visual QA → Judge`。每轮只解决一个明确问题，在隔离的 Git worktree 中修改，再用相同页面状态和视口采集结果。修改前先查找并复用已批准的 Token、组件和交互模式；确需新增时必须说明原因，并生成 Design Foundation 更新提案。Harness 保留计划、执行日志、代码状态和前后证据，不自动推送、合并或部署。

哪个编码 agent 来改都行，所以权限边界只声明一次：非交互、只写 run worktree、不自动加载被审仓库里的指令文件、不能 push / merge / 部署、有轮次或时长上限。每个适配器必须说明自己如何满足每一条，说不清的直接拒绝运行而不是降低保证。边界靠两层守：参数和环境属于预防，run 前后给宿主仓库取指纹属于检测，后者不依赖 agent 配合。

### 6. Learning System

记录 Accept / Reject、原因和上下文，把稳定结论沉淀为版本化 Expertise、Evaluator 规则、正反案例和回归测试。人的一次反馈不能直接改写全局规则；它先成为候选判断，经过归纳和回归验证后再发布为新版本。

## 当前已经完成

- Experience Spec v0.1：项目背景、证据、Finding、优先级输入、提案和判断。
- Design Foundation 数据结构：品牌、Token、组件、状态和交互模式可以进入项目 Spec，并区分已观察、已批准和已废弃。
- 本地 Harness CLI：初始化运行、采集 before、确认 Finding 是否仍成立、生成 agent Brief、隔离执行、采集 after、结构检查和 Accept / Reject。
- 安全门槛：过期证据不能进入 agent；错误页面不会被当成有效截图；同一运行不能静默覆盖证据或重复判断。
- HappyClaw 实例：已对基线 `cf1da7b` 与修改 `17314f0` 完成匹配的桌面和手机前后采集。改版来自现有草稿 PR，最终产品判断仍保持 pending。
- 产品首页和 Review Workbench：可以展示 Experience Spec、问题排序、agent Brief 和人工判断。
- Skill 注册表：26 个产品设计 Skill，带版本，只能挂白名单里的处理器，每次运行的结果产物不可变。
- 诊断：把 Skill 结果和 Spec 观察合并成带版本的证据图，去掉根因完全相同的重复项，记录可追溯的优先级。六个维度的 rubric 没覆盖齐、或者证据覆盖率不到 80% 时，Experience Score 保持空值，不给近似分。
- Expert Loop 状态机：每个阶段都会报出下一步该做什么，被阻塞时附上原因，`pnpm harness next` 直接打印。
- Agent 适配层：Codex 和 Claude Code 两个适配器共用同一条声明过的权限边界，各自的验证程度记在 run 账本里。
- 独立 Visual QA：截图层面的判断单独记录审阅者和版本，没通过之前不能 accept。
- Workbench 读取已导出的 run：`pnpm harness export` 把一次运行发布到 `public/runs/`，页面按 Expert Loop 阶段、诊断 Finding、前后截图、结构检查和已记录的判定展示。

## 尚未完成

- 自动浏览多页面和完整用户任务，而不只是指定 URL。
- 用真实案例校准 Experience Score 的评分器。现在只有闸门，证据不足时拒绝给分，但没有校准过的分数。
- 完整的 Design Foundation 清单。现在能盘点 CSS 自定义属性名、组件文件和重复的字面色值，但结果只是 observed 候选，Token 归一化、组件状态审计和漂移检测还没做。
- Design Foundation 的审核、发布、组件预览和变更历史界面。
- 项目级历史、Git 变更触发和增量 Review。
- Feedback 到 Expertise 新版本的审核、发布和回归机制。
- 多租户托管、支付、Deep Review 交付和订阅。
- 从 Experience Spec 驱动的高质量网站生成。

## 推荐实施顺序

1. **跑通一次全新的 agent 闭环。** 从未修改的真实 App 开始，由 Harness 生成任务、遵循已批准的 Foundation、执行代码修改和复查结果。两个已注册的适配器都还没完成过这样一次运行。
2. **把 Design Foundation Inventory 做完。** 现在能从真实仓库盘点出属性名、组件文件和重复色值，还缺 Token 归一化、组件状态审计和漂移检测。批准状态本身 Workbench 已经在显示了，缺的是审核和发布的操作界面，那条单列在「尚未完成」里。
3. **给 Workbench 配一个本地服务。** 已导出的运行现在能读了，但接入项目、覆盖优先级和看 diff 还只能用 CLI。
4. **补任务级浏览。** 支持登录以外的多步操作、状态快照和关键路径检查，使体验评估不止于首页视觉。
5. **校准评分器。** 六个可解释维度和证据覆盖阈值已经在诊断里了，缺的是用真实案例校准误报和漏报，再决定要不要公开总分。
6. **建立 Project Memory 和增量 Review。** 监听页面、组件与关键流程变化，只复查受影响部分。
7. **建立 Expertise 版本与回归集。** 把人的判断转为可审核规则，验证不会破坏已有案例后再发布。
8. **验证商业闭环。** 用 `$20 Deep Review` 获取真实用户和反馈，再验证持续订阅是否有足够频率和价值。
9. **加入网站生成。** 复用已经批准的品牌、组件、规范和评价体系，提供从诊断到生成的一体化服务。

MVP 的完成标准是：独立开发者提交一个可运行 App 和一个关键任务后，能够在一个工作区里得到可追溯的问题、完成一次隔离修改、看到匹配的前后证据，并给出接受或拒绝理由；过程中无需手工把 UX 建议重新翻译成 agent Prompt。
